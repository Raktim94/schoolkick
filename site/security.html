Security and privacy: what is in place, and what is not

School data is about children. This page lists the controls that exist in the code today and the ones that do not.

In place and tested

  • Default deny. Every API route must name the roles that may call it, or be marked public on purpose. A test calls every route without signing in and expects refusal.
  • Tenant isolation in two layers. Queries filter by institution, and the database also enforces it with row-level security, so a forgotten filter returns nothing instead of another school’s rows.
  • Teachers see only their classes. Guardians see only learners linked to them. Both are checked on the server for every request.
  • Append-only record. Attendance events and the audit log cannot be updated or deleted. A database trigger and a privilege restriction both refuse it.
  • Passwords are hashed with scrypt. Sessions are random tokens stored hashed, sent in an HttpOnly, SameSite cookie, and are revoked on sign-out.
  • Request protection. Writes need a custom header and a same-origin check. Sign-in and sign-up are rate limited. Request bodies are size limited.
  • Browser protection. A strict content security policy, no framing, and no third-party scripts, fonts or trackers on any page.
  • Minimal data. A learner record holds a name and an optional student ID. There is no analytics and no advertising.

Not done yet

  • No independent security audit or penetration test.
  • No two-factor sign-in, single sign-on or password reset by email.
  • No legal review for any country. Child-data rules differ by region, so check them before real use.
  • Backups are yours to run. The self-hosting guide shows how, and recovery has not been rehearsed for you.

If you find a vulnerability, please report it privately through the repository’s security advisory form.
